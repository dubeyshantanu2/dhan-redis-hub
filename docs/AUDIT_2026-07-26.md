## Verdict

**The transport works. The data contract does not.**

Every HTTP endpoint is up and returns real Dhan data — I fetched option chains, expiry lists, quotes, intraday and daily candles, and the scrip master live and got valid payloads for all of them. That part is genuinely done.

But three things that the docs record as working are **not** working, and I proved each one by executing it rather than reading it:

1. **A single Redis key serves two different instruments' prices.** 2,486 security IDs are ambiguous. A request for an MCX GOLD option returns a BSE small-cap's price.
2. **Kronos — the one project marked migrated — throws `AttributeError` on every option-chain and expiry fetch.** Its options paths have never worked through the hub.
3. **The WebSocket tick feed (FR-5) has never delivered a single tick** and cannot, as written.

The 8/8 green test suite and the green `/` health check do not detect any of these. Neither did the previous audit recorded in the vault.

## Critical

### C1 — One Redis key, two instruments: quotes are silently wrong

`poller.py:179` — `cache_key = f"dhan:quote:{security_id}"`. **No exchange segment.** Dhan security IDs are unique only *within* a segment. Parsing Dhan's own scrip master: **2,486 IDs appear in more than one segment.**

| Colliding pair | Shared IDs | Who is exposed |
|---|---|---|
| `NSE_CURRENCY` ↔ `NSE_EQ` | 2,411 | stock-screener, Kronos |
| `IDX_I` ↔ `NSE_EQ` | 71 | **ARES, Aeolus** (index spot vs equity) |
| `BSE_EQ` ↔ `MCX_COMM` | 3 | **Kronos** (MCX) |

Live proof against production:

```
security_id=511016  →  BSE_EQ=PREMCAP  |  MCX_COMM=SILVER-28Aug2026-272000-CE
   BSE_EQ    HTTP 200 in 1.16s -> last_price=5.34   (cold fetch)
   MCX_COMM  HTTP 200 in 0.58s -> last_price=5.34   (cache HIT — wrong instrument)

security_id=513496  →  BSE_EQ=SIZEMASTER  |  MCX_COMM=GOLD-27Nov2026-166000-CE
   MCX_COMM  HTTP 200 -> last_price=347            (the equity's price)
```

A bot asking for a gold option's price receives a ₹347 small-cap equity price. No error, no warning. Whoever queries first within the 5 s TTL poisons the key for everyone else.

**Fix:** `dhan:quote:{exchange_segment}:{security_id}` — change `poller.py:179`, `client.py:126`, `ws_feed.py:76` in one commit (all three must move together or reads and writes desynchronise).

### C2 — Scrip master: 21 MB blob, 13 s on a *cache hit*, and equity tickers are unresolvable

`poller.py:22-62`. Four projects depend on this (Kronos, stock-screener, Aeolus, gamma-blaster). Three defects compound:

**(a) It cannot resolve a ticker.** The parser prefers `SEM_CUSTOM_SYMBOL`, which for equities is a display name, not a ticker:

```
scrip_map["RELIANCE"] -> None      (CSV has TRADING_SYMBOL='RELIANCE', CUSTOM_SYMBOL='Reliance Industries')
scrip_map["TCS"]      -> None
scrip_map["INFY"]     -> None
scrip_map["SBIN"]     -> None
```

Ticker → `security_id` is the *only* reason to call this endpoint. It does not work.

**(b) 9,130 instruments (4.2%) silently dropped.** 218,412 CSV rows collapse into 209,282 keys because the map is keyed by symbol alone. 8,613 keys collide; 7,459 span more than one exchange. `RELIANCE INDUSTRIES` can hold NSE `2885` *or* BSE `500325` — whichever row was parsed last wins.

**(c) 21 MB round-trip, 13 s even when cached.** Measured back-to-back: call 1 = 12.35 s, call 2 (cache hit) = **13.00 s**. On a hit the path is Redis `GET` 21 MB → `json.loads` → FastAPI re-encode → transfer — all on a **512 MB** VM, all blocking the event loop. Against the `<2 ms` NFR this is ~6,500× over.

**Fix:** key by `f"{TRADING_SYMBOL}:{exchange}:{segment}"`, and serve a filtered subset (`?segment=NSE_EQ`) instead of the whole blob.

### C3 — Kronos's option-chain and expiry paths are hard-broken

The one project marked ✅ in the migration checklist. `Kronos/src/fetcher/dhan_client.py` calls methods its vendored client does not define:

```
Kronos DhanRedisClient.get_auth          -> DEFINED
Kronos DhanRedisClient.get_option_chain  -> *** MISSING ***     called at dhan_client.py:149
Kronos DhanRedisClient.get_expiry_list   -> *** MISSING ***     called at dhan_client.py:170
Kronos DhanRedisClient.get_quotes_batch  -> DEFINED
Kronos DhanRedisClient.get_quote         -> DEFINED
Kronos DhanRedisClient.get_candles       -> DEFINED

>>> c.get_option_chain(symbol="NIFTY", expiry="2026-07-28", ...)
AttributeError: 'DhanRedisClient' object has no attribute 'get_option_chain'
```

`dhan_client.py:147-159` has **no try/except**, so this propagates — the direct-REST fallback on line 160 is never reached. For an options scanner, the option chain *is* the product.

Kronos's quote and candle paths do work (I pulled real RELIANCE data through them). The vault's "193/193 tests pass" and "zero REST fallbacks verified" are both true and both missed this, because no Kronos test exercises the hub-enabled chain path.

### C4 — WebSocket tick feed (FR-5) has never worked

Two independent blockers in `ws_feed.py`:

- **Never subscribes.** Dhan's v2 feed requires a subscription frame after connect. There is no `ws.send` anywhere in the file. `_subscribed_instruments` (line 20) is initialised and never read again. Dhan therefore sends nothing.
- **Cannot parse a tick if one arrived.** Line 69 reduces binary frames to `{"raw": message.hex()}`; lines 71-74 then look for `security_id` / `LTP`, which that dict never has. The `publish` on line 81 is unreachable.

`dhan:ticks:*` has never carried a message. `client.subscribe_ticks()` (advertised in README:56) blocks the caller's thread forever with no error. **Argus is an orderflow/volume-profile system — ticks are its core input.**

**Fix:** implement the subscribe frame + `struct.unpack` of the v2 header, *or* delete `ws_feed.py` and strike FR-5 from the docs until someone needs it. Do not leave it advertised-but-dead.

---

### C5 — Every endpoint is unauthenticated on a public URL

`app.py` has no `Depends`, no middleware, no API key — verified by grep. `POST /quote` with any `security_id` is a guaranteed cache miss and therefore a real outbound call on your **shared live brokerage account**. Anyone who finds the URL can exhaust the Dhan quota and re-create the exact 429 problem this service exists to prevent. `/sync-auth` also returns the brokerage `client_id`.

**Fix:** one `X-Hub-Key` header dependency on the app, `GET /` exempt. ~10 lines.

## Medium

- **`TTL_OPTION_CHAIN_OFFMARKET` is dead config** — defined at `config.py:29`, never read. PRD FR-4's 60 s off-market TTL is unimplemented.
- **No market-hours gate** — the poller hammers Dhan every ~5 s at 3 a.m. and on weekends, and keeps the process busy enough to interfere with Fly's idle detection.
- **`load_dotenv()` is never called** despite `python-dotenv` being a dependency — the README's `cp .env.example .env` flow silently does nothing locally.
- **`auth_sync` takes `response.data[0]`** with no `ORDER BY`, no active filter, no expiry check (`auth_sync.py:24-31`). PostgREST row order is unspecified; Postgres relocates updated tuples.
- **`docker-compose.yml` maps `8000:8000`** but `start.sh` serves on `8080` — the README's `docker-compose up -d` yields an unreachable service. The compose image also starts a *second*, unused Redis.
- **`None` is overloaded** across "no data" / "hard failure" / "rate limited", all mapped to HTTP 502 — bots cannot choose retry vs skip.
- **Fresh `httpx.AsyncClient` per call** (8 sites) — full DNS+TCP+TLS handshake on every upstream request.
- **Discord webhook URL logged verbatim** on any non-2xx (`alerts.py:52,100,134`).
- **Dhan access token in the WebSocket URL query string**, logged on handshake failure (`ws_feed.py:38-41,55`).
- **429 alert embeds the varying backoff value**, defeating `alerts.py`'s own 60 s dedup.

## SDK Fork

The two clients have diverged, and **neither is a superset**:

| Method | hub `client.py` | Kronos `dhan_redis_client.py` |
|---|---|---|
| `get_option_chain` / `get_expiry_list` | ✅ | ❌ **missing → C3** |
| `get_quotes_batch` | ❌ | ✅ |
| `get_scrip_master` / `subscribe_ticks` | ✅ | ❌ |
| Redis-failure fallback to HTTP proxy | ❌ **raises** | ✅ via `_redis_get()` |

Proven: the hub's `client.py` cannot fall back to the proxy at all, because the Redis `GET` sits *outside* the `try` (`client.py:99`):

```
hub client.get_expiry_list("NIFTY") with no local Redis
   -> ConnectionError: Error 61 connecting to 127.0.0.1:6399. Connection refused.
Kronos client.get_quote(2885,"NSE_EQ") with no local Redis
   -> dict: {'52_week_high': 1611.8, ...}   # falls back correctly
```

Since no external bot can reach the hub's Redis (bound to `127.0.0.1`), **the proxy path is the only path that matters — and `client.py` cannot take it.** Following the migration guide's "copy `client.py`" instruction gives the six pending projects a client that fails on every call.

Also in the guide but wrong: `get_quotes_batch` doesn't exist; the documented `get_option_chain(symbol, underlying_scrip, underlying_seg, expiry)` argument order does not match the actual `(symbol, expiry, underlying_scrip=13, underlying_seg="IDX_I")`; and `DhanRedisClient(timeout=...)` raises `TypeError`.

`client.py:58,92` also default `underlying_scrip=13` (NIFTY) for **every** symbol — `get_option_chain("BANKNIFTY", expiry)` without an explicit scrip caches **NIFTY data under the BANKNIFTY key** for 12 h. Nothing errors; strikes and greeks look plausible.
